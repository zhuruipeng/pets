# 账号体系：宠物 App 与官网统一账号能不能复用

> 2026-09-30 评估。起因：「注册可否用我官网的注册页面代码复用」。
> 结论先行：**页面代码搬不过来，但有三处真正值得复用的东西**，其中
> 短信通道是**当前最该复用的**——因为宠物 App 自己压根发不出验证码。
>
> **2026-09-30 更新：老板拍板 cn 版走 A（共用账号），代码已落地。**
> 实施记录见文末「六、A 方案落地记录」，那里也是上线前要做的配置清单。

## 一、两套账号现在的样子

### 官网（`weiyuantool.com/account`，「出岫统一账号」）

单页 HTML + 原生 JS，`site/account/index.html`。后端在
`server/auth_center.py` + `server/api_routes/identity_02.py`。

| 能力 | 接口 |
| --- | --- |
| 发短信验证码 | `POST /api/auth/sms/send` `{phone, scene: "login"｜"bind_phone"}` |
| 短信登录（**未注册自动建号**） | `POST /api/auth/login-sms` `{phone, code}` |
| 手机 + 密码登录 | `POST /api/auth/login-password` |
| 重置密码 | `POST /api/auth/password-reset/request` + `/confirm` |
| 员工账号登录 | `POST /api/login` `{username, password}` |
| 微信扫码登录 | `GET /api/auth/wechat/config` → `POST /api/auth/wechat/exchange` |
| 首次微信登录绑定手机号 | `POST /api/auth/wechat/bind` `{bind_token, phone, code}` |
| 当前账号 | `GET /api/auth/me` |
| **换业务域令牌** | `POST /api/auth/erp-token` `{company_id}` |

短信是**真发**的：`server/auth_center.py::_send_aliyun_sms` 直接打阿里云
`dysmsapi.aliyuncs.com`（HMAC-SHA1 签名，零第三方依赖）。缺环境变量时抛
「短信服务未配置」，除非 `APP_SMS_DEBUG=1`。

### 宠物 App（M6）

Flutter 侧 `app/lib/ui/auth_sheet.dart`，服务端 `server/app/auth.py`。

| 能力 | 接口 |
| --- | --- |
| 发验证码 | `POST /auth/code/request` `{channel: "sms"｜"email", target}` |
| 验证即注册 | `POST /auth/code/verify` `{channel, target, code, device_id}` |
| 退出 / 我的资料 | `POST /auth/logout` / `GET /me` / `PATCH /me` |

### 差别一览

| | 官网统一账号 | 宠物 App |
| --- | --- | --- |
| 标识 | 仅手机号（11 位） | 手机号**或邮箱** |
| 密码 | 有（可登录、可重置） | **没有**，只用验证码 |
| 微信 | 有（扫码 + 首次绑手机） | 表里有 `users.wechat` 列，**未实现** |
| 短信 | 阿里云，生产可用 | **`sms_provider` 为空**，只在 dev 回显 |
| 令牌作用域 | 账号域（再换 ERP 域） | 宠物域 |
| 数据落点 | 境内 | cn 境内 / intl 海外，**互不连通** |

## 二、为什么「页面代码」搬不过来

三件事挡着，且都不是能靠翻译解决的：

1. **技术栈**：官网是 HTML + 原生 JS（`fetch` + `localStorage`），
   App 是 Flutter/Dart（`http` + SQLite）。没有共用代码的可能，
   只有「照着做一遍」。
2. **后端是两套服务**：官网账号表在 ERP 那套库里（`sms_codes` / 账号中心），
   宠物服务端是自己的 PostgreSQL，两区部署、数据不出境。
3. **令牌语义不同**：官网 token 是**账号域**，进任何业务系统都要再换一次票
   （`/api/auth/erp-token` 就是这个用途）。宠物服务端的 token 是**宠物域**。
   直接透传等于把两个信任域混成一个。

## 三、真正能复用的三样

### 1. 短信通道（最急，也最值）

宠物服务端 `server/app/config.py` 里 `sms_provider: str = ""`，
`dev_echo_code: bool = True` —— **上线后除了开发环境回显的码，用户拿不到码，
一个都登不进来**。

cn 区最终**没有搬代码**，而是直接共用官网那条发送链路 —— 既然账号本来就共用，
短信也共用同一条，宠物服务端不必自己有短信通道（见第六节）。

复用可行性已实查（2026-09-30，读服务器 `/root/财务软件.env` + 阿里云 `Query*` 接口）：

| 项 | 实况 |
| --- | --- |
| 签名 `ALIYUN_SMS_SIGN_NAME` | **`临沂未远工具`** —— 是**公司名**，不是产品名 |
| 模板 `ALIYUN_SMS_TEMPLATE_CODE` | `SMS_141655133`，状态「审核通过」 |
| 模板正文 | `您正在申请手机注册，验证码为：${code}，5分钟内有效！` |
| 正文里有没有品牌名 | **没有**，纯通用文案 |
| `APP_SMS_DEBUG` | 未设置 → **不会**静默降级成回显码，是真在发 |

结论：**不需要另报模板**。用户收到的是
`【临沂未远工具】您正在申请手机注册，验证码为：123456，5分钟内有效！`
—— 签名叫「未远工具」而不是某个产品名，所以从哪个业务发出来都不违和。
（这一条先前被我判反了：我看到模板「登录即注册」的场景名，就先入为主
以为签名写的是产品名。**没核实就不要下这种结论。**）

> 唯一轻微不匹配：正文写「申请手机注册」，而老用户是在**登录**。
> 但**这不是宠物 App 引入的** —— 官网自己的 `/api/auth/login-sms` 也用同一条
> 模板，官网登录场景下用户早就在收这句话。真想改就改现有这条模板
> （阿里云支持改后重审），不必新增。

顺带弄清了一个之前被我写错的点：`_send_aliyun_sms` 的 scene→模板映射是
`ALIYUN_SMS_TEMPLATE_{SCENE}`，找不到就回退 `ALIYUN_SMS_TEMPLATE_CODE`。
服务器上**只配了后者**（没有 `..._LOGIN` / `..._REGISTER`），所以任何 scene
最终都走同一条模板 —— **scene 不决定模板**。它真正的用途是
**验证码在 `sms_codes` 表里的隔离维度**（`_hash_code(phone, scene, code)`）。

### 2. 换票模式（统一账号才需要）

若决定共用账号，抄 `/api/auth/erp-token` 的形状，给宠物服务端加
`POST /api/auth/pet-token`：拿统一账号 token 换宠物域 token。
这样「一个手机号一个账号」，将来网页端也能看宠物数据，
且宠物服务端不需要理解统一账号的内部结构，只认一次换票结果。

### 3. 交互骨架（已经在无意中对齐了）

两边的登录形状本来就一样：手机号 → 6 位验证码 → 60 秒倒计时 →
未注册自动建号。差异只有「密码」和「微信」。所以 UI 层没什么可搬的 ——
**该搬的是上面两条，不是页面**。

## 四、三条路线

| | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **A 共用账号** | App 调官网短信/登录，换宠物域票 | 一个手机号一个账号；网页端可见宠物；短信成本合并 | 宠物服务端要加信任校验；**intl 版不能用**；丢掉邮箱登录 |
| **B 只借短信** | 账号仍独立，只接阿里云通道 | 最快（半天）；两区各自独立，合规干净 | 同号注册两次；两套短信费用 |
| **C 不动** | 继续 dev 回显 | 零成本 | **上线即不可用** |

**建议**：cn 版走 A（长期最省事），intl 版必须走 B
（数据不出境是架构红线，海外用户也没有出岫账号）。
短期想先跑通上线，就先 B、之后按需升级到 A。

## 六、A 方案落地记录（2026-09-30）

**cn 版走 A**（共用出岫统一账号），**intl 版保持 B 的形态**（自有账号，
将来接邮件通道）。区域差异全部收敛在 `core/region.dart` 的
`unifiedAccountBaseUrl` 里：cn 返回官网地址，intl 返回 `null`，
业务代码只判断「这个值是不是 null」，不判断区域。

### 登录链路（cn）

```
用户填手机号
   ↓
官网 POST /api/auth/sms/send {phone, scene:"login"}   ← 短信由官网发
   ↓
用户填验证码
   ↓
官网 POST /api/auth/login-sms {phone, code}           ← 拿【账号域】令牌
   ↓
宠物服务端 POST /api/v1/auth/unified {unified_token}  ← 换【宠物域】令牌
   ↓
之后就都是宠物域的事（同步、共养），与账号域无关
```

### 改了什么

| 位置 | 改动 |
| --- | --- |
| `server/app/unified.py`（新） | 换票接口 + 官网 `/api/auth/me` 的调用与解析 |
| `server/app/config.py` | 加 `unified_account_base_url`、`unified_account_timeout_seconds` |
| `server/app/main.py` | 挂载 `unified.router` |
| `app/lib/core/region.dart` | 加 `unifiedAccountBaseUrl`（cn 有值 / intl 为 null） |
| `app/lib/data/sync/unified_api.dart`（新） | 官网接口的独立客户端 |
| `app/lib/data/sync/sync_api.dart` | 加 `exchangeUnified()` |
| `app/lib/providers.dart` | 发码 / 登录两个方法按区域分流；新增 `unifiedAccountApiProvider` |
| `app/lib/ui/auth_sheet.dart` | cn 区不显示邮箱通道，改为一句说明 |

### 四条设计决定（都不是随手写的）

1. **官网令牌用完即弃，绝不入库。** 它只在换票那一次请求里存在。
   把账号域令牌存进宠物库，等于让一张凭证跨两个信任域长期有效，
   而且两边各自吊销的能力就废了。
2. **宠物服务端去问官网「这是谁」**（`GET /api/auth/me`），而不是自己验签 ——
   官网令牌是不透明随机串，宠物端验不了。代价是换票时多一跳，
   换来的是**自动继承官网的撤销语义**：用户在官网登出，拿旧令牌换票立刻失败。
3. **官网不可达时不建任何用户**（返回 503，不是「先建个空号」）。
   让一次网络抖动建出半个账号，用户下次登录会看到两个自己，且没法合并。
4. **已存在的用户不覆盖昵称。** 宠物 App 里的昵称是宠物圈里展示的名字，
   用户可能刻意和 ERP 账号名不同；每次登录都同步成官网昵称，
   等于把他改过的名字反复抹掉。

### 上线前必须配的（cn 区）

```bash
REGION=cn
UNIFIED_ACCOUNT_BASE=https://www.weiyuantool.com   # 必须带 www，见下
```

⚠️ **`www` 不是笔误，配掉会静默失效。** 裸域 `weiyuantool.com` 对**所有**请求
（含 POST）都返回 301 到 `www.weiyuantool.com`，而 Dart 的 `HttpClient`
**对非 GET 的 301 不自动跟随** —— 客户端拿到的是 nginx 那张
`301 Moved Permanently` 的 HTML 页，不是 JSON。

实测（`dart tool/probe_unified_account.dart`）：

| 地址 | 结果 |
| --- | --- |
| `https://weiyuantool.com` | `status=301`，无重定向记录，body 是 HTML |
| `https://www.weiyuantool.com` | `status=400 {"detail":"请输入正确的中国大陆手机号"}` —— 请求完好到达 |

阴险之处在于 **GET 会自动跟随、POST 不会**：手工 `curl` 探一下
`/api/auth/me`（GET）看着一切正常，真发码（POST）却永远失败。
所以 `region.dart` 的默认值、这里、以及测试里都钉死了 `www`。

官网那边**已经配好了，不用动**（实查为准）：

```bash
ALIYUN_SMS_ACCESS_KEY_ID=<已配>
ALIYUN_SMS_ACCESS_KEY_SECRET=<已配>
ALIYUN_SMS_SIGN_NAME=临沂未远工具
ALIYUN_SMS_TEMPLATE_CODE=SMS_141655133
APP_SMS_DEBUG=（未设置，正确）
```

另外两个部署约束（实查 nginx 得到）：

- 官网 `location /` 走 `proxy_pass http://erp_backend`，所以 `/api/...` 现在
  是 ERP 后端的。**宠物服务端要另起 upstream / 另开子域**，别去挤 `/api/`。
- `^~ /v1/` 与 `= /health` **已被占用**（反代到一个 fcapp 运行时）。
  宠物服务端若挂到同一个域名下，**不能占这两个路径**。

### 部署后自检

```bash
cd app
dart tool/probe_unified_account.dart                  # 用 region.dart 的默认地址
dart tool/probe_unified_account.dart https://xxx.com  # 或指定地址
```

用**真正的 `UnifiedAccountApi`** 打官网，验「发码端点是否 400 且带中文提示」
「身份接口是否 401」。退出码非 0 即有失败项。

之所以能用 `dart.exe` 直接跑：这条链路只依赖 `dart:*` 与 `package:http`，
`core/region.dart` 零 import、`unified_api.dart` 不碰 Flutter ——
本机那个「非提权进程起不了 flutter」的限制（`CreateFile failed 231`）不适用。
脚本只发**必然被拒**的请求（空手机号、假令牌），不会真发短信、不写库、
不消耗限流配额。

### 还欠着的两件

1. **共用 60 秒限流**：官网与宠物 App 用同一个 `scene=login`，所以
   「刚在官网点过发码，再来 App 点」会被拒。这其实是「同一个账号」应有的
   行为（他收到的就是同一条短信），但如果用户投诉，就要考虑分场景。
2. **intl 版仍发不出验证码**（`sms_provider` 为空、`dev_echo_code=True`）。
   海外区要接邮件通道，或者用阿里云国际短信。

> 原本这条还有一样「另报短信模板」—— **已核实不需要**，理由见第三节。
> 所以 A 方案在排期上**没有等待期**，只等宠物服务端自己部署好。

### 验证情况

- 服务端：`server/tests/test_unified.py` **50 项**断言全过（真跑，含
  「注释里的符号名不误报」「官网 401 判成令牌无效」「响应缺手机号判成契约破损」
  「网络不通判成不可达」等）。其中关键一条是
  **`parse_me_payload` 对空手机号返回 None** —— 空手机号会让唯一键判断失效，
  每次登录新建一个账号，是最坏的一类静默错误。
- 客户端：`app/test/unified_api_test.dart`（请求路径/请求体/UTF-8 中文错误消息/
  空 token 拦截/双斜杠防护/`cn 默认地址必须带 www`/`301 要提示地址被重定向`），
  需在管理员终端跑 `flutter test` 收口。
- 生产自检：`dart tool/probe_unified_account.dart` **本机已真跑**。
  默认地址全绿（发码端点 400 + 中文提示、身份接口 401）；
  故意传裸域则报 2 项失败并以退出码 1 结束 —— 双向都验过。
