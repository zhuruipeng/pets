# 海外区部署手册

> 目标：让 `api-intl.weiyuantool.com` 指向一个 **REGION=intl** 的实例，
> 它连**独立的 `pet_intl` 数据库**。这样海外用户的数据与中国区在
> PostgreSQL 层面就分开了，隐私政策里「海外用户数据不会回流境内」才成立。
>
> 全程**不需要买新服务器** —— 就在现有那台上再起一个进程。
> 前提假设：现有服务器仍是通过 `api.pet.weiyuantool.com` 提供中国区服务的那台。

## 先看清隔离做到了哪一层

| 层 | 做法 | 挡住了什么 |
|---|---|---|
| 数据库 | 新建 `pet_intl` 库，用户仍为 `pet` | 一次误连 `DATABASE_URL` 也不会把海外数据写进中国区库 |
| 进程 | 端口 8201（现有 8200） | 内存 / CPU 互相影响 |
| systemd | `pet-api-intl.service` | 单独启停、单独重启 |
| 私有 /tmp | `PrivateTmp=true` | 两区共享 `/tmp` 时上传的文档、导出的图片互相可见 |
| 域名 | `api-intl.weiyuantool.com` | 两区访问日志分开，出问题能追溯到具体区域 |
| 区域标记 | `REGION=intl` | ICP 展示位关闭、返回给客户端的区域信息正确 |

**注意 `cross_border_allowed` 会是 `false`，这是对的**。那是架构红线
（数据不出境），对每个区域恒为 `false`，不要当 bug 改。隔离靠的是独立数据库。

## Step 3 · 填 SMTP 授权码

**这是让登录真正可用的关键一步。**

### 3.1 拿授权码（腾讯企业邮箱要三步，不是一步）

**第 1 步 · 管理员放行**（只有管理员能做）

企业微信管理后台 → **协作 → 安全管理 → 客户端访问权限** →
修改「Exchange/IMAP/SMTP 服务范围」→ **勾选你的账号**

> ⚠️ 管理员没勾你的账号，用户端做多少步都连不上。这是最常见的卡点。

**第 2 步 · 你自己开两个开关**

浏览器登录 `exmail.qq.com`（建议企业微信扫码）：

1. **设置 → 收发信设置** → 勾选「**开启 IMAP/SMTP 服务**」→ 保存
2. **设置 → 邮箱绑定** → 点「**开启安全登录**」→ 确认

**第 3 步 · 生成授权码**

仍在「**设置 → 邮箱绑定**」页面 →「客户端专用密码」→ **生成新密码** →
填个识别名（如 `pet-api`）→ **立即复制那串 16 位密码** → 确定

> ⚠️ 关掉弹窗没复制 = 密码丢了，得删掉重新生成。

### 3.2 服务器参数（腾讯官方值）

| 项 | 值 |
| --- | --- |
| SMTP 服务器 | `smtp.exmail.qq.com` |
| 端口 | **465** |
| 加密 | SSL |
| 密码 | 上面那串 16 位授权码，**不是登录密码** |

（连不上时才换备用节点 `hwsmtp.exmail.qq.com`）

### 3.3 填进 `.env`

```sh
nano /opt/pet-api-intl/.env
```

```sh
SMTP_USER=noreply@weiyuantool.com
SMTP_PASSWORD=你的16位授权码
SMTP_FROM_EMAIL=noreply@weiyuantool.com   # 必须是后台已验证的发件人
```

> ⚠️ `SMTP_FROM_EMAIL` 必须是**已在企业邮箱后台验证过的发件地址**，
> 而且该地址要**真实存在于企业邮箱里**（没配这个域名就发不出去）。
> 不一致的话邮件会**进垃圾箱**，表现是「服务端说发出去了、用户说没收到」，
> 而日志一切正常。

## Step 4 · 起服务并自检

```sh
systemctl start pet-api-intl
curl -s localhost:8201/health
```

**期望看到**：

```json
{"status":"ok","region":"intl","icp_display_required":false,"cross_border_allowed":false}
```

- `region` 是 `intl` ✅
- `icp_display_required` 是 `false` ✅（境内才要 ICP 展示位）
- `cross_border_allowed` 是 `false` ✅（架构红线，不是 bug）

如果 `region` 不是 `intl`，检查 `.env` 里 `REGION=` 那行。

## Step 5 · 加 DNS 记录

在域名服务商那里加一条 **A 记录**：

| 主机记录 | 类型 | 线路 | 指向 |
| --- | --- | --- | --- |
| `api-intl` | A | 默认 | `124.223.174.129` |

`deploy/dns-add-record.py` 可以参考做法，**但请先手动确认再跑** ——
DNS 改错会影响所有人，而且解析生效可能要等几分钟。

### ⚠️ 踩过的坑：控制台显示「生效」但公网解析不到

这次实际卡了很久，三个原因叠在一起：

1. **「主机记录」填的是相对于「当前所选域名」的部分**。
   域名列表里选中 `weiyuantool.com` 时填 `api-intl`，得到的是
   `api-intl.weiyuantool.com`。
   本项目最终就用这个（与中国区 `api.pet.` 的层级不对称，
   但**数据隔离由独立数据库保证，不受影响**）。

2. **控制台的绿点「生效」只代表记录已保存，不代表公网能查到**。
   判断要看实际查询：

   ```sh
   # 查权威服务器（绕过所有缓存，最准）
   dig +short A api-intl.weiyuantool.com @eric.dnspod.net

   # 查公共 DNS（确认已传播）
   dig +short A api-intl.weiyuantool.com @223.5.5.5
   ```

   查不到时**看状态码**：`NXDOMAIN` = 记录根本不存在（加错地方了），
   超时 = 网络问题。两者方向完全不同，必须分清。

3. **先查权威、再看公共**。公共 DNS 有缓存，权威才是真相。
   顺序反了会误判成「还没生效」而白等。

## Step 6 · 签证书

DNS 生效后：

```sh
certbot certonly --webroot -w /var/www/acme -d api-intl.weiyuantool.com
```

## Step 7 · 补上 443 配置

```sh
bash /opt/pet-api-intl/deploy/08-nginx-intl.sh
```

第一次跑会自动先写 80 段（证书还没有），签完证书再跑一次就补上 443。

> 这个脚本刻意做了保护：**证书不存在时绝不写 443 段**。
> 因为 nginx reload 时会读 `ssl_certificate` 指向的文件，文件不在就直接
> 启动失败 —— 而那会连累同机器上的官网和 ERP（正在跑的生产业务）。
>
> 脚本在 `nginx -t` 失败时会**自动还原**并且**不 reload**。

## Step 8 · 端到端验证

```sh
# 1) 健康检查
curl -s https://api-intl.weiyuantool.com/health

# 2) 邮件通道（换成你自己的邮箱）
curl -s -X POST https://api-intl.weiyuantool.com/api/v1/auth/code/request \
  -H 'Content-Type: application/json' \
  -d '{"channel":"email","target":"你的邮箱@example.com"}'
```

**期望**：收到邮件，标题里带 6 位验证码；响应 `{"sent":true,...}`。

**如果响应 503**：`verification channel is not configured` —— 说明 `.env` 里
SMTP 三项没填全。这个报错是特意加的：**宁可明确报错，也不要假装发出去**
（之前 `_dispatch_code` 是 `return None`，接口却返回 `sent: true`，
用户盯着手机等一分钟什么都没有）。

**查发送日志**：

```sh
journalctl -u pet-api-intl -f | grep -i "smtp\|code email"
```

| 日志里出现 | 原因 |
| --- | --- |
| **生成不了授权码** | 管理员没在「客户端访问权限」勾你的账号，或没开「安全登录」 |
| `smtp not configured` | `.env` 里 host/user/password 没填全 |
| `smtp auth failed ... AUTHORIZATION CODE` | 填成了**登录密码**，必须用 16 位授权码 |
| `smtp send failed` + 握手错误 | 端口与 TLS 不匹配（465 配 `true`、587 配 `false`） |
| `code email sent to xx***@domain` | SMTP 发送成功 |
| 成功但**用户说没收到** | `SMTP_FROM_EMAIL` 不是已验证发件人 → **邮件进垃圾箱** |
| 提示域名无法发送 | `SMTP_USER` / `SMTP_FROM_EMAIL` 用的地址没真实存在于企业邮箱里 |

**「成功但用户说没收到」最难查**：SMTP 一切正常、服务器无异常，只有收件人看不到。
排查顺序：先查垃圾箱 → 再确认发件地址已在后台验证 → 最后用一封普通邮件测。

**建议**：第一次先发到自己的常用邮箱，确认收到了再上。

## 出问题怎么回滚

海外区是**新增**的，回滚不影响中国区：

```sh
systemctl disable --now pet-api-intl
rm /etc/nginx/conf.d/pet-api-intl.conf && nginx -t && systemctl reload nginx
```

数据库 `pet_intl` 可以先留着（里面只有测试数据），
确认不要了再 `DROP DATABASE pet_intl;`。

客户端要回滚的话，把 `app/lib/core/region.dart` 里
`API_BASE_INTL` 的默认值改回去并重新打包即可。

## 常驻问题

**Q：需要买新服务器吗？**
不需要。这个方案就是在现有机器上多起一个进程。真正要买的那天，
理由会是负载或可用性（单点），不会是「数据隔离」。

**Q：以后用户多了怎么办？**
先把 `pet-api-intl` 迁到独立机器上。**迁移时务必带走整个 `pet_intl` 库** ——
那才是数据，配置文件随时能重建。
