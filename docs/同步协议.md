# 多设备同步协议 v1

这份文档是**契约**：客户端（Flutter）与服务端（FastAPI）按它实现，任何一侧单独改动
都会造成静默的数据丢失或重复。改协议必须同时改这份文档。

---

## 一、目标与硬约束

| 约束 | 含义 | 为什么绕不开 |
| --- | --- | --- |
| **离线优先** | 没网也能记，联网后自动补同步 | 遛狗时在地下车库、电梯里是常态 |
| **数据不出境** | 中国用户数据只在中国节点，海外只存海外节点 | 免掉 PIPL 出境评估、GDPR 的 SCCs/TIA（见 README 架构约定 2） |
| **多设备** | 同一账号多台手机各自记，最后收敛到一致 | 用户会换机、会同时有手机和平板 |
| **共养** | 一只宠物可被多个账号读写 | `members` 表从 M1 就建好了 |
| **软删除** | 删除是写墓碑（`deleted_at`），永不物理删 | 硬删 + 离线设备 = 已删数据被"复活"回来 |
| **弱网友好** | 一次遛狗 1800 个轨迹点，不能逐点同步 | 变更日志会被轨迹点撑爆 |

**不做**的事：不做 CRDT、不做操作日志回放、不做字段级合并。理由是这些都需要
"业务语义可交换"，而宠物记录（用药剂量、体重）恰恰不能自动合并 —— 见第六节。

---

## 二、术语

- **scope**：一条数据归属谁。所有业务数据最终挂在某只宠物下，`pet_id` 就是同步的分发键。
- **seq**：服务端全局单调递增序号（BIGSERIAL）。客户端用它当拉取游标。
- **outbox**：本地"待推送变更"队列。由 SQLite 触发器自动写入，仓储层不用管。
- **墓碑（tombstone）**：`deleted_at` 非空的行。它要同步，否则别的设备永远不知道删过。
- **LWW**：Last-Write-Wins，按 `updated_at`（毫秒）比大小。

## 三、同步范围

| 表 | 同步 | 说明 |
| --- | --- | --- |
| `users` | ✅ 仅自己那一行 | 只同步 `nickname` / `phone` / `email` / `wechat` / `contact_note`；不含 token |
| `pets` | ✅ | 主体档案 |
| `members` | ✅ | 共养关系。权限判定也靠它 |
| `records` | ✅ | |
| `attachments` | ⚠️ 仅元数据 | 图片文件走独立上传通道（M6 不做，`remote_url` 字段已预留） |
| `reminders` | ✅ | |
| `reminder_logs` | ❌ v1 不同步 | 它是**本机行为统计**，跨设备合并意义不大；且表里没有 `updated_at`，要同步得先补列。完成率在 v1 里各设备各算各的 |
| `walk_sessions` | ✅（含轨迹点） | 见下方说明 |
| `walk_points` | ❌ 不逐行同步 | 作为 `walk_sessions` 的子数组一起传 |
| `pet_tags` | ❌ v1 不同步 | 当前没有任何写入路径（防丢标签是 M5 之后的功能） |
| `sync_outbox` / `sync_meta` | ❌ | 纯本地机制 |

> 实现侧的唯一事实来源是 `app/lib/data/db/schema.dart` 的 `kSyncedTables`：
> 同步范围靠它的触发器决定（**不是**靠仓储里手写「记一笔」）。改这张表要同时看那份清单。

### 为什么 `walk_points` 要特殊处理

一次遛狗按每秒一个点算有 1800 个点。逐行同步的代价：

1. 变更日志每次遛狗涨 1800 行，pull 端要下载 1800 条 JSON 对象；
2. 轨迹点**不具备独立语义** —— 不能单独编辑、不单独删除，只随 session 生死。

所以约定：`walk_sessions` 的同步载荷里带一个 `points` 数组（`[{lat,lng,alt,acc,t}]`）。
推送时整体替换，拉取时整体覆盖本地该 session 的点。**点坐标不做冲突合并** ——
两个设备同时遛同一只狗是罕见场景，真发生就整段覆盖，不猜。

## 四、服务端数据模型

```sql
-- 变更日志：同步的心脏。一张表装下所有表的变更，客户端只认一个游标。
CREATE TABLE sync_changes (
  seq         BIGSERIAL PRIMARY KEY,     -- 全局单调递增，就是 pull 游标
  table_name  TEXT   NOT NULL,
  row_id      TEXT   NOT NULL,
  op          TEXT   NOT NULL,           -- upsert | delete（墓碑）
  pet_id      TEXT,                      -- 分发键；users 行为 NULL
  user_id     TEXT   NOT NULL,           -- 变更发起者，便于排查
  payload     JSONB  NOT NULL,           -- 行快照，不是 diff
  changed_at  BIGINT NOT NULL            -- 变更发生时间（毫秒）
);
CREATE INDEX idx_sync_changes_seq ON sync_changes(seq);
CREATE INDEX idx_sync_changes_pet ON sync_changes(pet_id, seq);

-- 登录令牌。用不透明随机串而不是 JWT：令牌要能立刻撤销（换手机、丢手机）。
CREATE TABLE auth_tokens (
  token       TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL,
  device_id   TEXT,
  created_at  BIGINT NOT NULL,
  expires_at  BIGINT NOT NULL,
  revoked_at  BIGINT
);

-- 验证码。手机与邮箱共用一张表。
CREATE TABLE verify_codes (
  id          TEXT PRIMARY KEY,
  channel     TEXT NOT NULL,        -- sms | email
  target      TEXT NOT NULL,        -- 手机号（E.164）或邮箱（小写）
  code        TEXT NOT NULL,
  purpose     TEXT NOT NULL,        -- login | bind | invite
  tries       INT  NOT NULL DEFAULT 0,
  created_at  BIGINT NOT NULL,
  expires_at  BIGINT NOT NULL,
  consumed_at BIGINT
);
```

`members.role` 取值：`owner` / `editor` / `viewer`。

| 权限 | owner | editor | viewer |
| --- | --- | --- | --- |
| 读全部数据 | ✅ | ✅ | ✅ |
| 写记录 / 提醒 / 遛狗 | ✅ | ✅ | ❌ |
| 改宠物档案 | ✅ | ✅ | ❌ |
| 邀请 / 移除成员 | ✅ | ❌ | ❌ |
| 删除宠物 | ✅ | ❌ | ❌ |

## 五、接口契约

所有接口前缀 `{区域后端}/api/v1`。认证走 `Authorization: Bearer <token>`。
**两个区域各自独立部署，同一份代码、不同数据库，彼此不知道对方存在。**

### 5.1 认证

```
POST /auth/code/request     { channel: "sms"|"email", target: "..." }
   → { sent: true, expires_in: 300, dev_code?: "123456" }   # dev 环境才回码
POST /auth/code/verify      { channel, target, code, device_id }
   → { token, user: {...}, expires_at }
POST /auth/logout           → { ok: true }   # 撤销当前 token
GET  /me                    → { user: {...} }
PATCH /me                   { nickname?, phone?, email?, wechat?, contact_note? }
```

规则：
- 同一 target 60 秒内只发一次码（防刷）；同一 IP 每小时上限 20 次。
- 验证码 6 位数字、5 分钟有效、错 5 次作废。
- 首次验证即注册（`users` 行自动创建，`region` 取服务端自己的区域）。
- **手机号统一存 E.164**（`+8613800138000`），邮箱统一小写。

### 5.2 同步

```
POST /sync/push
{
  "device_id": "uuid",
  "changes": [
    { "table": "records", "row_id": "r1", "op": "upsert",
      "updated_at": 1730000000000, "payload": { ...行快照... } },
    { "table": "walk_sessions", "row_id": "w1", "op": "upsert",
      "updated_at": 1730000000000, "payload": { ..., "points": [...] } }
  ]
}
→ {
  "applied":   [ { "table": "records", "row_id": "r1", "result": "applied" } ],
  "rejected":  [ { "table": "records", "row_id": "r9", "result": "stale" } ],
  "server_seq": 1042
}
```

```
GET /sync/pull?since=<seq>&limit=200
→ {
  "changes": [
    { "seq": 1001, "table": "records", "row_id": "r1", "op": "upsert",
      "payload": {...}, "changed_at": 1730000000000 }
  ],
  "next_since": 1042,
  "has_more": false
}
```

规则：
- **push 幂等**：同一条变更重复推送，`updated_at` 比不过服务端现值就返回 `stale`，不写库。
- **push 的顺序无关**：服务端逐条 LWW，不要求客户端按时间排序。
- **pull 的可见范围**：`pet_id` 在「我是成员的宠物」集合内，或 `user_id = 我` 的 users 行。
  这层过滤在服务端做 —— 客户端不可信。
- `limit` 上限 500，超出按 500 处理。`has_more` 为真时客户端应立即用 `next_since` 续拉。
- `next_since` **在没有变更时也返回当前 seq**，客户端可以直接存下来。

### 5.3 共养

```
POST /pets/{pet_id}/members/invite
  { channel: "sms"|"email", target: "...", role: "editor"|"viewer" }
  → { invite_id, sent: true }

GET  /pets/{pet_id}/members          → [ { user_id, nickname, role, status, joined_at } ]
GET  /members/invites/mine           → [ { invite_id, pet_id, pet_name, role, invited_at } ]
POST /members/invites/{invite_id}/accept   → { ok: true }
DELETE /pets/{pet_id}/members/{user_id}    → { ok: true }   # owner 才能删
```

规则：
- 邀请目标**必须是已注册用户**。没注册就提示「让对方先注册」，不做短信邀请裂变
  （那需要模板报备，且用户量不够时是纯成本）。
- 邀请发出后写一条 `members` 行，`status = pending`；接受后置为 `active`。
- `pending` 状态下**没有读权限** —— 邀请不等于授权。
- 成员变更本身也要进 `sync_changes`（`pet_id` = 该宠物），否则别的设备看不到新成员。
- **`GET /members/invites/mine` 是必须的**：被邀请人此时还不是 `active` 成员，
  pull 的可见性过滤会把他自己那条 `members` 变更挡在外面 —— 光靠同步，
  他永远不知道自己被邀请了。
  （不需要在邀请上另存 target：邀请发出时手机号/邮箱就已经解析成 `user_id` 了。）

## 六、冲突解决

**规则：按行 LWW，比 `updated_at`（毫秒）。平局服务端胜。**

- 客户端推送时带本地的 `updated_at`；服务端与库里现值比较，**大者胜**（`>` 才覆盖，相等不动）。
- 拉取时客户端同样比较：远端 `changed_at`/`payload.updated_at` 不大于本地就跳过。
- **墓碑参与比较**：删除也是一次写入。如果删除发生在某次编辑之前，编辑会"复活"这一行 ——
  这是 LWW 的固有行为，接受它。反过来（编辑后又删除）删除胜，符合直觉。

**为什么不做字段级合并**：两条记录同时被编辑时，"合并"意味着猜。
比如两台设备各自改了体重（23.4 / 23.6），合并出一个 23.5 是**凭空造数据**。
宠物健康数据宁可丢一次编辑，也不能造出一个用户没填过的值。
真要减少冲突，方向是减少并发写（共养时用提醒引导"谁来记"），而不是合并算法。

**已知限制（明确接受）**：
1. 两台设备离线各改同一行 → 后同步的那次编辑丢失，**会丢**，不提示。
2. 设备时钟不准 → LWW 判断错。缓解：推送时服务端记录 `received_at`，
   但比较仍以客户端 `updated_at` 为准（否则离线补传会被误判成旧数据）。
3. 附件文件本身不同步（只同步元数据）。

## 七、客户端引擎

### 7.1 变更捕获：用 SQLite 触发器，不改仓储

**关键决策**：每张业务表挂 `AFTER INSERT` / `AFTER UPDATE` 触发器，自动往
`sync_outbox` 插一条待推送记录。

为什么不用「在仓储的每个写方法里手动记一笔」：仓储有六个（pets / records /
attachments / reminders / walk / member），写方法二十多个，还分软删、恢复、
批量写入等分支。**漏一处就是一类数据永远不同步，而且只在那条路径上复现。**
触发器由数据库保证，绕不过去。

```sql
CREATE TRIGGER trg_records_outbox AFTER INSERT ON records BEGIN
  INSERT INTO sync_outbox(table_name, row_id, pet_id, op, updated_at)
  VALUES ('records', NEW.id, NEW.pet_id,
          CASE WHEN NEW.deleted_at IS NULL THEN 'upsert' ELSE 'delete' END,
          NEW.updated_at);
END;
-- UPDATE 触发器同理；每个同步表两条（INSERT / UPDATE）
```

`sync_outbox` 上 `(table_name, row_id)` 建唯一索引，同一条行被改多次只留最后一次
（`INSERT OR REPLACE`）—— 中间态没必要推。

### 7.2 抑制回环

从服务器拉下来的变更**不能再进 outbox**（否则推上去又拉下来，无限循环）。

做法：应用远端变更时不走触发器 —— 设一个连接级的开关标志
（`sync_meta.applying = 1`），触发器里 `WHEN (SELECT value FROM sync_meta WHERE key='applying') <> '1'`。
这比"先删 outbox 再补"可靠，因为不依赖操作顺序。

### 7.3 一次同步的完整流程

```
1. 若未登录 → 直接返回
2. push：取 outbox（按 updated_at 升序，批 200）→ POST /sync/push
   - applied → 从 outbox 删除
   - stale   → 也删除（服务端已有更新的，本地这条是旧版本，推不上去也别卡住队列）
3. pull：GET /sync/pull?since=<sync_meta.last_seq>
   - 逐条按 LWW 应用到本地（applying=1 期间）
   - 更新 last_seq = next_since；has_more 则回到 3
4. 记录 last_sync_at
```

**先 push 后 pull**：如果反过来，会先把远端的旧版本拉下来覆盖本地新改动，
再推上去导致自己的改动丢一次。先推后拉是唯一安全的顺序。

### 7.4 触发时机

- App 进入前台（`AppLifecycleState.resumed`）
- 每次写操作后延迟 2 秒（防抖，避免连记 5 条就同步 5 次）
- 设置页「立即同步」
- 都失败就静默重试（指数退避，最多 5 分钟一次），**错误不弹窗打断用户**

## 八、本地表结构变更（schema v4）

```sql
-- 联系方式（M5）
ALTER TABLE users ADD COLUMN wechat TEXT;
ALTER TABLE users ADD COLUMN contact_note TEXT;

-- 同步状态
CREATE TABLE sync_meta (key TEXT PRIMARY KEY, value TEXT);
-- key: device_id / last_seq / last_sync_at / account_id / applying

CREATE TABLE sync_outbox (
  table_name TEXT NOT NULL,
  row_id     TEXT NOT NULL,
  pet_id     TEXT,
  op         TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (table_name, row_id)
);
```

`users` 表原先只有 id/nickname/phone/email/avatar_url/region —— 够用，
联系方式只加了两个字段（`wechat` 和自由文本 `contact_note`，留给"其他联系方式"）。
